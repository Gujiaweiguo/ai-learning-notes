## 一、毕业作品进度：最后一步不是"跑一遍"

```
D1 ✅ Ontology Model（Entity + Identity + Relationship）
D2 ✅ Lifecycle + Event Model（迁移声明 + Guard 挂载）
D3 ✅ Rule Model（四物种 Rule Card）
D4 ✅ Capability + Policy + Skill Mapping（执行三角）
D5 ✅ Agent Mapping（数字员工 Agent Card）
D6 ✅ 组装（六条装配规则 = 符号解析）+ 验证设计（三组对照夹具 + L1→L5 判定梯 + 判分表）
D7 📍 跑验证、出报告 —— 今天，四周轨道收官
```

昨天你设计了测试套件。今天要跑，但**跑验证的产出不是"通过"两个字，是一份验证报告**。这两者的区别，就是"演示"和"验证"的区别——你在 26 年 ERP 生涯里见过无数次前者冒充后者：Demo 环境跑通、领导点头、上线翻车。

今天建立的核心认知只有一条：

> **验证报告不是通过证书，是证据集 + 闸门裁决 + 缺陷账本。**
> 一份只写"验证通过"的报告，价值为零；一份写清"测了什么、什么没测、发现了什么缺陷、凭什么放行"的报告，才是 AI 时代数字员工的验收交付物。

## 二、真实材料锚点：你早就发明过"验证列"

看 MI `capability-traceability-matrix.md` 的五列：`legacy → spec → anchor → **verification** → status`。每个能力行都带着 verification 列——能力级验证你在 MI 里已经制度化。今天的动作不是发明验证，是**把验证从能力级升两级**：

```
能力级验证（MI 追溯矩阵已有）  →  这个能力的代码锚点存在且可追溯
员工级验证（今天新增）        →  这名数字员工在具体业务问题上行为正确
模型级验证（今天新增）        →  支撑它的 Semantic Model 六层推理链不断链
```

为什么必须升两级？因为能力级验证的对象是"锚点存在"（静态追溯），而数字员工的问题永远是动态的："A101 为什么不能出租？"——答案不在任何一列里，在**六层模型的推理链上**。验证对象因此也变了：**不是答案，是轨迹（trace）**（D6 §五已裁决），今天跑的就是采轨迹。

## 三、跑验证的三件事：正跑、对照、盲测

D6 的验证设计给了三组夹具（A101 反例 / A102 正例 / A103 边界例）和判定梯。今天执行时要加两个 D6 没有定式化、但验证学里缺一不可的动作：

### 3.1 正跑：采集三条 trace

对三个夹具各跑一遍 L1→L5，每跳记录 evidence ID（身份路径 / 迁移 T2/T3 / Rule ID / Policy 条目 / capability ID）。产出不是"对/错"，是**三条可审计的轨迹**——它们进报告附录，构成证据集。

### 3.2 对照基线：证明验证有判别力

**最容易被跳过、也最致命的一步。** 验证体系本身也需要验证：它杀得住错模型吗？方法是引入一个**故意做错的对照 Agent**——"快照式 Agent"，它不推理，直接信任落库的 `available` 字段（D-001 Amendment A 明确反对、但行业里 90% 系统实际在做的方式）。

| 夹具 | 快照式 Agent（基线） | 语义模型 Agent | 判别力 |
|---|---|---|---|
| A101（退租卡住） | 不可租（快照 stale=False，碰巧对） | 不可租 + CRE-R-003 守卫证据 | 无判别 |
| A102（干净铺位） | 可租（碰巧对） | 可租 + CRE-R-002 推导 | 无判别 |
| A103（预定已过期） | **不可租（错！快照停留在预定期间）** | 可租 + T3 事件 + CRE-R-008 | **✅ 杀住** |

如果基线和被测对象得分一样，你的验证等于没验——所有模型都通过的系统，不是模型好，是**测试松**。A103 就是专为此设计的杀手锏夹具（D6 §4.1），今天它完成了使命：**快照式实现在它身上翻车，语义模型活了下来**——这才叫验证有判别力。

### 3.3 盲测：设计之外的新世界

再往 D6 的三组夹具上加一个**验证设计时没讨论过**的新夹具 A104（例如：铺位资产状态 Active，但 `restriction_flag = 资质审查中`，落库快照还写着 available=True）。它考验泛化：模型的 Rule Card 谓词结构（`Space.restriction_flag == absent`）是在 D3 写死的声明，不是为夹具定制的 if-else——盲测夹具就是检验"声明的泛化力"。语义模型 Agent 走 CRE-R-002 的 restriction 分支判"不可租"，快照式 Agent 再次答错。

> 正跑证明"设计内正确"，对照证明"验证有牙齿"，盲测证明"设计外不崩"。三者合起来，报告里的"通过"才有含金量。

## 四、验证报告的七段结构（今天的交付格式）

这是今天真正要沉淀的**文体**。数字员工验证报告不是文章，是结构化文档：

| # | 段 | 内容 | 回答什么 |
|---|---|---|---|
| 1 | **范围** | 夹具清单（A101-A104）、场景（铺位可租性）、判定梯版本 | 测了什么 |
| 2 | **判定结果** | 夹具 × L1→L5 判分矩阵，必达项状态 | 过没过 |
| 3 | **对照证据** | 基线 Agent vs 语义 Agent 的判别力对比 | 验证本身有效吗 |
| 4 | **缺陷账本** | 验证过程中发现的问题，每条带 ID + 严重度 + 归属层 | 发现了什么 |
| 5 | **覆盖声明** | 没测什么（多项目并发 / Variant 规则 CRE-R-020 / 审批流全链） | 结论的边界 |
| 6 | **闸门裁决** | PASS / PASS WITH CONDITIONS / FAIL + 放行条件 | 准不准上线 |
| 7 | **v0.2 待办** | 缺陷账本 → 下一版模型的输入 | 然后呢 |

四段是关键增量，逐个说：

**缺陷账本（第 4 段）——验证的价值主要在这里。** 跑完今天的验证，真实发现至少三条：
- **DEF-01**：A102/A103 上 L4/L5 全部 n/a——动作建议能力只覆盖"卡住"场景，正常流转场景无建议可给。覆盖率 1/3。严重度：中。归属：Capability 层。
- **DEF-02**：A101 的 L4 轨迹引用的是"Policy② 层 conditional 授权"的**描述**，但 Policy 层还没有给这条授权正式编号——半悬空引用，六条装配规则查不到（它们查层间引用，不查层内编号完整性）。严重度：高。归属：Policy 层。
- **DEF-03**：CRE-R-020（进场守卫客户变体）没有任何夹具覆盖——Variant 物种在验证里缺席。严重度：中。归属：验证设计（不是模型的错，是测试的洞）。

注意 DEF-03 的归属：**验证发现的缺陷不全在被验证对象里，有些在验证体系自己身上**。能诚实记录这一条的报告，才可信。

**覆盖声明（第 5 段）——报告的诚实边界。** "铺位可租性问题在 4 个单铺位夹具上通过"≠"数字员工验证通过"。没测的：并发预定竞争、跨项目、CRE-R-020 万达/中旅变体、审批流全链（K1-K3 完整路径）、时间回拨。**验证结论的作用域永远 ≤ 夹具的作用域**——这句话写给未来读到"PASS"就兴奋的人，也写给六个月后翻旧账的你。

**闸门裁决（第 6 段）——三级，不是两值。** 今天的结果是典型的中间态：L1-L3 必达全绿（✅），L4 因 DEF-02 降级为"有条件"，L5 仅 A101 达成。裁决：**PASS WITH CONDITIONS**——条件 = DEF-02 修复（Policy 层补编号）后 L4 复验。上线可以，带账上线。"通过/不通过"的二元裁决逼人说谎，三级裁决让人说真话。

**v0.2 待办（第 7 段）——验证报告是下一版模型的输入。** 缺陷账本直接变成 Semantic Model v0.2 的 backlog。至此闭环合拢：

```
v0.1 模型 → 验证 → 报告（证据 + 缺陷） → v0.2 backlog → 再验证 → ……
```

这就是语义模型的 CI 循环——和你给 MI 代码写的测试流水线完全同构，只是被测物从代码换成了"企业业务世界的描述"。

## 五、四周毕业：四份交付物与一条主线认知

今天是四周轨道最后一天。盘点交付物：

| 周 | 交付物 | 一句话价值 |
|---|---|---|
| W1 | MI CRE Semantic Gap Analysis v0.1 | 已有 Domain Model 缺的不是模型，是显式语义 |
| W2 | MI CRE Ontology Graph v0.1 | 语义不从零设计，从已有材料抽取 |
| W3 | LangChat × Ontology × Compiler 集成方案 | 业务语义 → 能力 → 技能是编译链路，你已在做 |
| W4 | Semantic Model v0.1 + **验证报告** | 模型 + 证明模型可用的证据集 |

四周其实是同一个动作的四次重复，半径不断扩大：**把隐式的显式化，把显式的可验证化**。

- W1 发现：AI 读 Domain Model，语义是隐式的（读不出"Lease 终止后影响什么"）；
- W2-W4 把 Entity/Relationship/Lifecycle/Rule/Capability/Policy 一层层显式化；
- W6 装配规则让显式化的层间引用可机器检查；
- 今天，判定梯让"AI 是否真的理解"本身可验证、可审计、可迭代。

W1-D4 那个问题——"AI 读你的 Domain Model 能读懂吗？"——今天有了工程化的答案：**读懂与否不再靠感觉，靠 trace。每一跳携带 evidence ID 的推理轨迹，就是"理解"的可观测形态。**

## 六、连接思考（与主线 W12-D7 VirtualCTO 能力边界审视）

主线今天是 Vision Intelligence 周收官：VirtualCTO 审视能力边界——"AI 能做什么、不能做什么、边界怎么声明"。并行轨道今天是数字员工验证报告——"数字员工证明自己能做什么、证据在哪、覆盖到哪为止"。

两份文档是**同一种文体**：都不是宣传材料，都是边界声明。VirtualCTO 的能力边界如果不诚实，客户会在翻车处失去信任；数字员工的验证报告如果没有覆盖声明，业务方会在没测过的场景里失去信任。**AI 的可信度不来自宣称的能力上限，来自诚实声明的能力边界。** 你给 VirtualCTO 写的边界审视方法（哪里必须退给人、哪里需要人审），和判定梯的 L4/L5（Policy 判断 + 人审姿态）是同一件事的两种尺寸。两条轨道在"边界"这个词上完成最后一次交汇。

## 七、架构师视角

- **以前**：验收 = Demo 跑通 + 领导签字。验收报告是行政动作，产出是"同意上线"四个字。数字员工能不能干活的判断依据是演示视频和 PPT。
- **现在**：验收 = 夹具 × 判定梯 × trace 证据 × 闸门裁决。验证报告是工程产物：七段结构里最值钱的是缺陷账本和覆盖声明——**前者驱动 v0.2，后者防止过度信任**。而"PASS WITH CONDITIONS"成为最常见也最健康的裁决——带账上线、按账迭代，这才是一个活的语义模型的正常代谢。

## 八、练习（5 分钟）

1. 客户现场部署数字员工时，验证夹具该由谁定义？如果你的团队自造全部夹具，"PASS"在什么意义上失效？（提示：回到 §四 的覆盖声明——夹具决定结论的作用域，谁定义夹具，谁就定义了"通过"的边界。真实历史案例做夹具，为什么是唯一诚实的来源？）
2. DEF-02（Policy 授权无正式编号、半悬空）为什么会被六条装配规则漏掉？试着把它改写成一条第 7 条装配规则（W7），再想想：它和 D6 练习里你反驳过的那条候选规则（human_review_gate 与 delegation 矛盾）比，是层间引用问题还是层内完整性问题？该由组装审计器查，还是该由闸门裁决兜底？
