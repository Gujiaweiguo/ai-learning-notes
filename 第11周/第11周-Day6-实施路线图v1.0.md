## ━━━ 1. 今日核心问题 ━━━

### 为什么路线图不是"功能排期表"？

大多数 AI 平台的路线图长这样：「Q3 做多模型支持、Q4 做知识库增强、明年做 Agent 市场」。这是**产品功能视角**——按"客户能看见什么"排序。

LangChat v2 的路线图不能这么排。因为过去五天的代码现实扫描已经证明：**当前最大的风险不是缺功能，而是制品链语义不完整**——DeploymentRevision 以为闭包完整实际不完整，SkillRelease 这个名字在 v1/v2 指不同的东西，Connector 能力分散在三套互不相识的子系统里。

所以路线图的正确排序依据不是"客户想要什么"，而是三个架构问题：

1. **哪个 Gap 会在运行时爆炸？**（安全性优先）
2. **哪个 Gap 阻塞了最多下游工作？**（依赖优先）
3. **哪条链路现在就是断的？**（事实优先）

一句话：**先修地基，再盖楼，最后装修。** 这不是排期问题，是排序哲学问题。

## ━━━ 2. 人话解释（用 Jason 26 年 ERP 经验讲）━━━

Jason，这就像你做过的 ERP 大版本升级项目。

聪明的做法从来不是"把新功能全列出来按月排"，而是：

1. **第一阶段：先保住生产**——存量客户在用的 v1 canonical execution 不能坏。相当于 ERP 升级先冻结现有账套，做双跑准备。
2. **第二阶段：补齐核心档案**——KnowledgeSnapshot 缺失就像 ERP 里"没有 BOM 快照的生产订单"：订单跑的时候 BOM 被改了，成本核算全乱。这是第一个要补的。
3. **第三阶段：定接口契约**——RuntimeABI 缺失就像 ERP 标准模块和二次开发之间没有版本兼容承诺，每次升级都是灾难。这是第二个要补的。
4. **第四阶段：再做增量价值**——CapabilityRelease、Connector 统一抽象，这些是"让平台更好演化"的事。

错误的排序（先做 Connector、先做可视化、先做多模型）就像 ERP 项目先做报表美化再补基础数据——做得越快，死得越快。

## ━━━ 4. ADR 依据 ━━━

### ① v2 Target Domain Model §1.2（冻结的目标态边界）

30+ 对象中以下为当前路线图的 P0 对象：KnowledgeCollection/KnowledgeSnapshot、RuntimeABI、Capability/CapabilityRelease、DeploymentRevision 闭包完整性。文档明确警告：**把未实施对象写成"已落地"违反文档状态约定**——所以每个 Sprint 的验收标准必须用"代码事实"定义，不能用"文档说"定义。

### ② Charter §6.6（宪法约束）

> 任何运行时变更（依赖升级、配置变更、Knowledge 更新）必须生成新 DeploymentRevision。

这条约束是 Sprint 1 的直接依据：**没有 KnowledgeSnapshot，这条宪法就是空话**——知识变了根本无法生成新 Revision。

### ③ Charter §6.2（Single Canonical Execution Path）

只有一条 canonical 执行路径。这意味着所有补齐工作都必须**汇入**这条路径，而不是在旁边另起炉灶。Sprint 2 把 OCI 骨架和 canonical execution 打通，正是为了消除"两套平行体系"。

### ④ tools-call-external-provider-guard spec

外部 provider 工具只能通过 canonical SkillRelease 调用。这决定了 Connector 工作（Sprint 4+）必须以 SkillRelease 为载体，不能绕过制品链。

## ━━━ 5. 核心交付：LangChat v2 实施路线图 v1.0 ━━━

### 🏁 Sprint 0（1 周，预备）：术语清理 + 基线冻结

**为什么必须有 Sprint 0**：Day 2 发现的最大陷阱是"SkillRelease"在 v1（canonical execution，3710 行）和 v2（OCI 制品，~400 行骨架）指不同的东西。不先改名，后面所有 Sprint 的沟通和代码都会踩同一个坑。

**任务**：
- v1 SkillRelease canonical execution → 更名为 `CanonicalExecutionService`（或等效），释放 "SkillRelease" 这个名字给 v2 OCI 制品
- 冻结当前 Gap Matrix 作为基线（11 周笔记本 Day 2 文档为 v1.0 基线）
- 建立"目标态对象 ↔ 代码模块"对照表，进 AGENTS.md

**验收标准**：
- ✅ 代码库中 "SkillRelease" 一词只指 OCI 制品
- ✅ 存量 canonical execution 功能回归测试全绿
- ⚠️ 风险：改名波及面大 → 用 deprecation alias 过渡，不一次性改完

---

### 🔴 Sprint 1（2 周）：KnowledgeSnapshot — 补全部署闭包（最高优先级）

**为什么第一**：Day 2 + Day 4 的共同结论——DeploymentRevision 闭包缺 KnowledgeSnapshot = 执行不可复现 = "上周三数字员工回答了什么"无法追溯。这是**运行时会爆炸的合规风险**，且 Charter §6.6 宪法因它而悬空。

**任务**：
1. `KnowledgeCollection`（Business Domain）：当前 KnowledgeBaseModel 升级为逻辑集合语义，保留 tenant/workspace 隔离和跨空间挂载（Day 4 确认这些是好的）
2. `KnowledgeSnapshot`（Supply Chain）：新增不可变快照对象——对集合内容做内容寻址 digest，快照不可修改
3. 闭包接线：DeploymentRevision 增加 knowledge_snapshot_digest 字段
4. 变更链路：Knowledge 变更 → 新 Snapshot → 提示生成新 DeploymentRevision（可先做提示，不强制阻断）
5. Runtime 消费侧：`retrieve_rag_context` 读快照引用而非活集合（canonical 路径内）

**验收标准**：
- ✅ 同一 KnowledgeCollection 打两次快照，内容相同则 digest 相同
- ✅ 部署闭包中知识部分可回答"这次执行用了哪个版本的知识"
- ✅ 存量 RAG 检索质量回归测试不下降（RAG 工程层不动）

**风险**：快照粒度（文件级 vs 集合级）→ 先做集合级 digest（粗但够用），文件级留待后续。

---

### 🟠 Sprint 2（2 周）：RuntimeABI + OCI 打通 — 建立版本契约

**为什么第二**：Day 2 结论——Runtime 与制品之间无版本契约（当前靠 Python import 硬绑定），升级必爆炸。且 supply_chain/oci/（881 行）与 canonical execution（3710 行）两套平行体系必须合一，否则 Single Canonical Execution Path 是假的。

**任务**：
1. 定义 RuntimeABI：制品侧声明要求的 ABI 版本，Runtime 侧声明提供的 ABI 版本，加载时校验
2. Compatibility Matrix（已有 compatibility_matrix.py）接入实际加载路径，而不是静态摆设
3. OCI publish 骨架与 canonical execution 打通：SkillRelease（OCI 制品）发布 → digest-pinned → 可被 DeploymentRevision 引用
4. 明确"不可变"边界：制品发布后 content 不可改，metadata 可补注（referrers.py 已有骨架）

**验收标准**：
- ✅ ABI 版本不匹配的制品被 Runtime 拒绝加载，报错可读
- ✅ 一条端到端链路：Blueprint → IR → OCI SkillRelease → DeploymentRevision → canonical execute，全程 digest 可追溯
- ✅ 升级 Runtime 版本时，旧制品行为可预测（兼容或显式拒绝，不会静默改变行为）

**风险**：ABI 定义过细会拖慢迭代 → 第一版只约定 3 件事：入口签名、上下文对象、错误协议。

---

### 🟡 Sprint 3（2 周）：CapabilityRelease + 发布流 — 让能力可治理

**为什么第三**（Day 2 决策：可延后一个 Sprint）：Capability 当前可用（Catalog 评分 7），版本化缺失的迁移成本可控。但它阻塞"能力供应链"的完整叙事，必须在 Knowledge 和 ABI 之后、大规模接入行业能力之前完成。

**任务**：
1. Capability（语义）与 CapabilityRelease（制品）分离——Catalog 只管语义注册，Release 管不可变制品版本
2. ReleaseChannel 补 PromotionEvent（Day 2 发现 Channel 移动不留痕）
3. Deployment（当前仅 48 行）与 ReleaseChannel 联动：Channel 移动触发部署建议
4. Evaluation 关联：auto_trigger 从 release 评估扩展到 deployment 评估（Day 2 发现 DeploymentEvaluation 几乎空白）

**验收标准**：
- ✅ 更新合同查询 Capability 后，旧数字员工行为不变（引用旧 Release）
- ✅ 每次 Channel 移动有 PromotionEvent 审计记录
- ✅ 灰度发布（TrafficPolicy）从"有定义"变为"有引擎执行"——至少实现按百分比分流

**风险**：与现有 capability_gateway 的整合复杂 → 先并行后切换。

---

### 🔵 Sprint 4+（后续）：Connector 统一抽象 + Outbound System Bridge

**为什么最后**：Day 3 结论——段 3 连接能力最空白，但它不在"运行时爆炸"清单上（tools-call-external-provider-guard 已经挡住了不安全的调用路径）。且 Outbound System Bridge 10 个 Phase-0 Gate 只关闭 2 个（deadline 2026-08-22），设计本身还在 review-blocked，不宜抢跑。

**并行轨道（不占 Sprint 资源）**：
- 每周关闭 1-2 个 Phase-0 Gate，8/22 前完成证据收集
- MCP streamable_http transport 部署验证（代码已就绪）
- mcp_kit 连接池管理（当前每次新建 session）

**验收标准（Sprint 4 启动条件）**：
- ✅ Phase-0 Gate 关闭 ≥ 8/10
- ✅ Connector 统一抽象设计评审通过（以 CapabilityRelease 为载体）

## ━━━ 7. 与传统方案比较 ━━━

### 路线图方法论对比

| 方法 | 典型做法 | LangChat v2 适用性 |
|---|---|---|
| **功能驱动（MoSCoW）** | 按客户可见功能排序 | ❌ 会把装修排在地基前面 |
| **技术债驱动** | 按债的大小排序 | ⚠️ 债大≠风险大（SkillRelease 3710 行最大但不是最危险） |
| **风险驱动（本路线图）** | 按"运行时爆炸概率 × 合规影响"排序 | ✅ 安全性 > 完整性 > 美观性 |
| **架构演进驱动** | 按依赖链排序（闭包→契约→发布→连接） | ✅ 与风险驱动结论一致 |

### 与"Dify 式路线图"的对照

Dify 式路线图：功能列表 → 排优先级 → 冲刺交付。适合配置即应用的范式——因为没有制品链，每个功能独立。

LangChat 路线图：**对象语义补全 → 链路打通 → 治理前移**。因为制品链是环环相扣的，闭包不完整时后面全是空中楼阁。

## ━━━ 8. 架构师思考题 ━━━

### CTO 级问题

**场景**：Sprint 1 进行到一半，最大客户（20 个购物中心的商业地产集团）突然要求 4 周内上线"合同智能审查"功能，否则续约堪忧。这个功能依赖：新版合同政策知识库 + 一个新 Capability + 微信渠道触达。

**问题**：
1. 你会插队做这个功能，还是坚持路线图？插队的代价是什么？
2. 如果必须做，怎么在 Sprint 1 的 KnowledgeSnapshot 还没完成时，保证"这次合同审查用的知识版本可追溯"？（提示：临时手段 vs 架构手段的边界在哪）
3. 这个需求里哪些部分其实**不依赖** v2 对象（可以立刻用 v1 能力交付）？哪些部分踩在 Gap 上？

**提示**：回到 Day 5 的思考——客户真正买的是"确定性"。如果为了赶功能丢掉了确定性，就输掉了和"企业自建现状"竞争的唯一筹码。但拒绝客户也是死。**架构师的价值在于把需求拆开：哪些走快车道（v1 已有），哪些必须等制品链（v2 补全）。**

## ━━━ 9. 我的理解变化 ━━━

**以前以为**：实施路线图就是把 Gap Matrix 里的红色项按优先级排个序，工作量估一下。

**现在知道**：路线图的第一行不是任何 Gap，而是**术语清理**。因为 Day 2 发现的"SkillRelease 术语重叠陷阱"会让所有后续工作沟通失真——两个工程师说"SkillRelease"时指的是不同的东西，这种项目失败不是因为做得慢，而是因为说得岔。其次，路线图的排序依据是"运行时爆炸概率"，不是"Gap 大小"——3710 行的 v1 canonical execution 是最大的代码资产，但不是最危险的地方；最危险的是 DeploymentRevision 那个"以为完整实际不完整"的闭包。最后，路线图必须包含**验收标准用代码事实定义**这条元规则——因为 Target Domain Model §1.2 明确警告，把未实施对象写成已落地违反文档约定，路线图如果不防这一点，就会变成又一份自我安慰文档。
