# 第14周-Day6 Semantic Model v0.1定稿包：六构件组装（IMA完整版）

> 学习周：W14（MI CRE 开发期）· 补传版 · 对应产物：`semantic-model/mi-cre-semantic-model-v0.1.yaml`（机器可读）+ `.md`（人读版），双格式落盘
> 前置知识：D3 ontology 体检、D4 Rule 层对账、D5 覆盖率检查——本日把三天的证据组装成一份可消费资产

## 一、Semantic Model 是什么？为什么不是"又一份文档"？

**为什么学这个**：企业系统里从不缺文档——架构图、数据字典、领域模型、术语表，每份都过时。Semantic Model 的本质区别在于它是**分层 SoT 的索引与裁决层**：不复制下游源（ontology、BCM、Domain Model、registry、代码），只声明"什么在哪、谁说了算、哪里断了"。每个断言带证据指针（sha 指纹、文件路径、代码锚点），每个数字可重跑复算。

**在 LangChat/CRE 平台中的位置**：AI Agent 要在 472 张表、17 个 Context、883 条术语的复杂度里路由查询，需要一份"机器可校验的地图索引"。Semantic Model 就是这份索引——W15 的 term-aliases 生成（第一个消费方）直接吃它的术语层。

**生活类比**：它不是又一本旅游攻略，而是攻略、地图、公交系统的**联合索引页**：不重复各书内容，只告诉你"查历史去 A 书第 3 章、查路线用 B 图、两书对老城区边界说法不一致以 B 图为准、B 图有 10 处标注过时"。索引页的价值恰恰在于它不复制内容——复制会制造第二个需要同步的副本。

**定位一句话**：PT-W4 的 Semantic Model v0.1 草案是"文档"；本版把它升级为**机器可校验、可被消费的开发资产**。

## 二、宪章：分层 Source of Truth 五行表

组装的第一步不是收集内容，而是先立"谁说了算"：

| 层 | Source of Truth | 证据锚点 |
|---|---|---|
| 术语/别名 | business-ontology.yaml | sha256_16 = `bf550bc24de66813`（须补治理头，G-01/P0） |
| 业务能力/行 ID | CRE BCM（ADR-001~006） | 不可变锚点 |
| 对象归属/边界/生命周期 | MI Domain Model 17 Context | 472 表实证分布 |
| 规则/Effect | effect-registry.yaml v1.0 | 5 类冻结（2026-07-26） |
| 实现事实/验收 | openspec specs + 代码 | 273 specs |

**讲解 1（为什么宪章放最前）**：没有宪章的语义资产，消费方遇到冲突（D3 报告叫 `02 Party Core`、D5 代码现实叫 `02 Merchant`）只能猜。宪章把裁决规则前置：术语冲突听 ontology 的、归属冲突听 Domain Model 的、实现细节听代码的。**索引层的第一职责是裁决，不是描述。**

**讲解 2（sha 指纹的意义）**：给 ontology 打 sha256_16 指纹后，任何时点重算指纹做 diff，就能精确知道"语义资产漂移了多少"——熵增从感觉变成度量。这是全包可复算原则的基石。

## 三、六构件速览（每个构件 = 内容 + 证据指针）

### 3.1 Entity（实体骨架）
骨架 = 17 Context + Platform 桶，472 表实证分布（BI 14.8% 最大）。关键结构发现：**模块↔Context 是多对多**（财务管理模块涉及 4 个 Context；4 个 Context 无任何模块入口）——所以"模块名≈Context"的假设必然翻车，模块×Context 映射表是查询路由的必需品。

### 3.2 Identity（身份锚）
三层锚点：物理锚 = canonical_tables（472，双迁移并集裁判）；行锚 = BCM 行 ID；术语层 = 883 条 / 792 唯一 / 91 条复用待消歧。**讲解**：一个对象在不同层有不同的"身份证"，Identity 构件就是把三种证件的互查关系登记下来——AI 从术语进、从表出，中间要过两道身份翻译。

### 3.3 Relationship（关系）
语义侧 = 模块×BCM×Context 三维映射；实现侧 = 三个事务耦合点（occupancy.CreateTx / amendment 应收重算 / ar_rebalance）+ 12 条灰区。**讲解**：关系构件抓的不是外键，是**跨域耦合点**——三个事务耦合点是未来拆分/演进的最贵障碍，先登记先受益。

### 3.4 Lifecycle（生命周期）
lease 8 态（以代码枚举为准）、condition-approval 全生命周期审计、amendment 9 类矩阵数据化（运行时可编辑）。与 D4 对账结论一致：生命周期的 SoT 是代码枚举，不是文档。

### 3.5 Rule（规则）
5 类冻结 effect 的实现映射 + service-effect 不注册的决策档案。最大洞：frozen 无 CI（G-05）。**讲解**：这里特意收录"不注册"的评审理由——负空间也是语义，后来者不用再争论一遍。

### 3.6 Capability+Policy（能力与策略）
102 能力标签；role 覆盖 7/102，场景覆盖 15/102（全冻在资源管理）；policy 三载体（审批权矩阵/审批流策略/变更矩阵）。**讲解**：能力层是全包最稀疏的层——它如实声明了自己不完整（场景层断供预警），而不是装作可用。

## 四、已知缺口 10 条（G-01~G-10）：缺口即交付物

P0 一条：**G-01 ontology 无治理 frontmatter**（无版本/状态/维护人/变更流程）。其余按严重度：G-02 场景层断供、G-03 术语 91 条复用待消歧、G-04 名称漂移（D7 质检时自己踩中：Party Core vs Merchant）、G-05 registry 无锚无 CI、G-06 双迁移分叉、G-07 新表无挡板、G-08 断言未核、G-09 矩阵无快照、G-10 语义超额承诺。

**为什么缺口与构件同等重要**：W15 消费方拿到资产时，必须知道**什么不能信**。一份只写优点的语义资产等于让消费方蒙眼过桥。每条缺口带证据指针，可追溯到具体实验数据——缺口不是道歉，是风险定价表。

**类比**：药品说明书的不良反应栏——不是让药卖不出去，是让医生敢开处方。

## 五、熵增基线：为什么第一个消费方要赶时间

月度表增长实数：4月 68 → 5月 4 → 6月 152 → 7月 148 → 8月 98；跨切面桶占比 26.2% 且持续扩大。**语义资产不是被推翻死的，是被稀释死的**——不需要任何人否定 ontology，只需要每月 100+ 张新表不进任何语义锚点，检索命中率就自然衰减。结论：第一个消费方必须赶在稀释前面（W15-D3）。

## 六、关键组装决策（方法论沉淀）

1. **骨架选 Context 不选模块**：模块多对多、变动频繁（组织调整就变）；Context 有 472 表实证背书。任何以模块为骨架的语义索引都会在下次组织调整时报废。
2. **索引不复制**：复制下游源 = 制造第二个需要同步的副本（D3 锚点熵教训）。Semantic Model 每个条目只存"指针 + 裁决规则"，内容留在 SoT。
3. **缺口是交付物**：见第四节。
4. **service-effect 不注册写进档案**：负空间也是语义，见 3.5。
5. **消费方声明前置**：还没消费就先写"第一个消费方是谁、只能吃哪层、什么不能吃"——消费预警前置是资产可信度的一部分。

## 七、第一个消费方（W15-D3 执行案）

**选择**：从术语层 + Entity 锚点批量生成 LnkChatBI term-aliases / SQL 示例校准集。
**预警**：只能吃术语层（883 条中 792 唯一），场景层 15/102 冻结不可消费；91 条复用术语必须带消歧声明输出。
**为什么选它**：问答恰好只吃术语层——唯一完整可消费的面；语义错误的爆炸半径最小、可回滚、可度量（D7 Review 补充论证）。
