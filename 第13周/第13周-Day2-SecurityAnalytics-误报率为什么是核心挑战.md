# 📌 Security Analytics：入侵/越界/烟火/危险区域/离岗 —— 安全场景为什么误报率是核心挑战？

━━━ 1. 今日核心问题 ━━━

**安全场景为什么误报率是核心挑战？**

不是精度不高、不是延迟太大、也不是检测不到——是**误报**。

昨天 People Analytics 的痛点是"数据不准"（客流统计偏差 20%，报表还能用，只是要打折看）。今天 Security Analytics 的痛点完全不同性质：**误报不是质量瑕疵，是系统杀手**。一个商场一年真实火警接近 0 次，如果系统每月误报 3 次火灾，半年后保安看到告警的第一反应是"又是误报"——这时候系统已经在功能上死亡了，无论它的召回率是多少。

核心论断：**安全告警的价值不在"报得对不对"，而在"被不被当真"。误报率消耗的是信任本金，而信任本金一旦亏空，漏报风险反而放大**（真告警淹没在假告警里 = 变相漏报）。域知识.md 白纸黑字写着：误报率是"市场落地难度大"的**核心原因**——这是这个产品商业上最贵的一个技术指标。

━━━ 2. 人话解释（用 26 年 ERP 经验讲）━━━

Jason，这个你在 ERP 里被咬过：

**告警疲劳（alert fatigue）就是"狼来了"的工程学形式。** 你 26 年里一定见过这种系统：MRP 异常提醒每天弹 200 条，信用超额预警每周一准时群发，用户第三周开始全选已读，第六个月要求把它关掉。**告警系统的死亡曲线不是渐进的，是断崖的：信任一旦破产，用户不会"部分相信"你，是整体静音。**

安全场景把这个问题放大到极端，原因是一个 ERP 人最熟悉的词：**基数（base rate）**。

- ERP 月结异常：每月真异常可能有几十条 → 误报几十条还能忍，信噪比 1:1；
- 商场火灾：**一年真事件 0~1 次** → 就算检测器单帧精度 99.9%，对着每天几百次截图评估，一年误报几十次，信噪比 50:1 全是假的。

这就是为什么"把模型精度做到 99%"救不了安全场景——**先验概率太低，任何小于 100% 的精度都会被基数淹没**。你调低阈值，误报涨（狼来了）；调高阈值，漏报涨（火灾没报，法律责任）。**单靠一个 confidence 阈值，这道题无解**。所以真正的答案不是"更好的模型"，是"多层漏斗"——后面代码验证部分你会看到，MallSenseAI 已经在代码里摆了整整三层。

━━━ 3. LangChat（LnkChat）架构位置 ━━━

五层模型里，Security Analytics 的覆盖方式和昨天 People Analytics 不同：

```
L1  Image Understanding     — Detection（烟火/障碍物检测）        ← MallSenseAI 现有主力
L2  Video Understanding     — Tracking（跌倒/离岗需要的行为连续性）← 缺失
L3  Scene Understanding     — 危险区域占用/禁入区判定            ← 规则引擎部分覆盖
L4  Business Intelligence   — 安全事件工单/趋势                  ← Alert→WorkOrder 已有
L5  Vision Agent            — 自动研判/分级/日报                 ← 缺失
```

六个安全场景的分层落点（今天的关键地图）：

| 场景 | 需要的层 | 现状 |
|---|---|---|
| 烟火 | L1 + L3 | ✅ FireSmokeDetector（dfire-yolo11n） |
| 危险区域/禁入区占用 | L1 + L3 | ✅ forbidden_zone 规则 |
| 消防通道障碍物 | L1 + L3 | ✅ duration/area 规则（真实部署：消防梯/货梯厅） |
| 入侵/越界（周界） | L1 + L2（轨迹） | ⚠️ 只有 ROI 级退化实现，无越线事件 |
| 跌倒 | L2（姿态+时序） | ❌ 无 |
| 离岗 | L2（person + 时序） | ❌ 连 person 检测器都没有 |

结构判断：**六个场景按"误报治理难度"排序，恰好和"Tracking 依赖度"排序一致**。越接近纯 Detection 的场景（烟火/障碍物），误报越能靠几何+时长+冷却压制；越依赖时序行为的场景（跌倒/离岗/越界），单帧证据越弱，误报越难治。**误报率是横在 L1→L2 升级路上的真实动机，不只是精度问题。**

━━━ 4. ADR / 战略文档依据 ━━━

**① 域知识.md 设计决策 #1**：「暂不推广但维护运行……市场落地难度大（摄像头改造成本、物业付费意愿、**误报率**）」。
注意措辞：三个原因里，改造成本是钱的问题、付费意愿是市场的问题，**误报率是唯一的产品技术问题**——而且它和付费意愿直接联动（误报 → 物业不信 → 不付费）。

**② 域知识.md 已知限制（两条相邻，值得对照读）**：
- 「火灾检测**漏报率**未量化（安全 + 法律责任风险）」
- 「**误报率**未持续优化（这是"市场落地难度大"的核心原因）」

一漏一误并列出现，就是昨天 W10-D4 fail-closed/fail-open 思维的镜像问题：**安全检测的两种错误代价严重不对称**。漏报火灾 = 人命 + 法律责任，方向上必须宁可误报（fail-open 式的召回优先）；但误报又有信任死刑。两头都不许输，就是安全场景比客流场景难一个数量级的根源。

**③ FireSmokeDetector 的 `supplemental: True`**（代码 metadata，见 §5）：每一次烟火检测都自我标注为"补充性"。这是架构决策的代码化石——**视频烟火检测不是烟感器的替代，是补充**。传统烟感负责物理真相，视频检测负责早期可视证据。这个定位本身就是一种误报治理：把"唯一真相源"的信任责任分摊给物理传感器。

**④ 边界依据**：域知识「不做什么」明确排除消防联动/门禁控制（只告警 + 建工单，不做物理控制）。误报的最高代价被限制在"人跑一趟"，不是"喷淋启动"——**用边界控制误报的爆炸半径**，这本身就是治理设计。

━━━ 5. 代码验证（只看关键结构）━━━

三层误报防线，代码里已经全部存在：

**第一层：检测器内（一次性过滤）**——`backend/app/detectors/fire_smoke.py`：
```python
if conf < confidence_threshold: continue          # 置信度（默认 0.5，规则可覆盖）
if label.lower() not in _FIRE_SMOKE_LABELS: continue  # 类别白名单
if area_ratio < min_area_ratio: continue          # 面积下限（默认 1% 画面）
if roi_polygons and not _inside_any_roi(...): continue  # ROI 空间过滤
```
四道闸门，一次推理内完成。**同一个数字（conf）被空间（ROI）、类别（label）、尺度（area）三维加固**——这是"不靠单一阈值"的第一层体现。

**第二层：规则引擎（时间维度确认）**——`backend/app/rules/engine.py`：
```python
class ObstructionRuleEngine:
    """Stateless evaluator ..."""
    # cooldown_state: 负键存 first-seen，正键存 last-alert（rule_id × roi_id）
if active_seconds < min_stay_seconds: return None   # 持续性确认：瞬时出现不算
if not cls._is_cooled_down(..., cooldown_seconds, ...): return None  # 同一区域冷却
```
`min_stay_seconds` 是误报治理的核心武器：**单帧误检是噪声，持续占用才是事件**。用时间连续性对冲单帧证据不足——这正是"截图模式"（非视频流）下能用最低成本换到的时序证据。`cooldown_seconds` 治的是另一类误报的兄弟问题：**重复告警**（一个箱子在那里放三小时，不该每轮巡检都报一次）。

**第三层：人审（社会性确认）**——`backend/app/models/entities.py`：
```python
class AlertStatus(str, enum.Enum):
    ...
    false_positive = "false_positive"   # pending → confirmed / false_positive / resolved
```
`false_positive` 是 Alert 生命周期的**一等公民状态**：值班员标记误报是一个正式动作，不是删记录。这就是 W10-D4 学过的 human-in-the-loop 在视觉域的同构——**机器不确定的，最终由人来裁决，且裁决被结构化留存**。

**多副本一致性细节**（`rules/cooldown_store.py`）：冷却状态存 Redis hash，`setdefault` 用 `HSETNX` 保证并发 worker 竞争时"先写者赢"——误报治理的状态在分布式下也保持正确。

**最大的 Gap（把三条线连起来看）**：`false_positive` 状态被记录了，但**没有回流**——它没有变成下一轮的阈值调整依据、没有变成困难样本、没有进入任何学习回路。人审在做分类，系统不在学习。**误报治理目前是静态漏斗，不是闭环**。

━━━ 6. 商业地产映射 ━━━

| MallSenseAI 概念 | MI CRE 场景 | 商业含义 |
|---|---|---|
| forbidden_zone 规则 | 消防通道/禁入区占用告警 | 消防合规是物业的法定责任，这是刚需场景 |
| min_stay_seconds | "箱子堆了 10 分钟"才算障碍物 | 过路搬运 ≠ 违规，时长区分日常与违规 |
| cooldown（N 小时不重报） | 同一工单未处理期间不重复派单 | 物业工单系统去重，避免同一告警刷爆值班群 |
| AlertStatus.false_positive | 安保值班员的误报标记动作 | 最宝贵的标注数据：一线人员的时间成本换来的真值 |
| supplemental: True | 视频烟火 = 烟感的补充证据 | 消防验收责任主体仍是烟感系统，视频不背法律责任 |
| 烟雾误报（蒸汽/灯光） | 后厨蒸汽、夕阳反射 | 真实部署里最伤信任的两类"长得像火的正常现象" |

**给 MI 的战略提醒**：误报率是安防系统能否按"人效替代"收费的分水岭。误报 5% 的系统替代不了保安巡查（反而增加复核工作量）；误报 0.5% 的系统才能写进 SLA 卖订阅。**误报率直接决定这个产品的收费模式能不能成立。**

━━━ 7. 与传统方案比较 ━━━

**A. 视频烟火检测 vs 传统烟感**：
- 烟感：物理真相（粒子浓度），误报源是蒸汽/烟尘，但**有国标背书、责任清晰**；
- 视频检测：早期可视证据（烟雾可见即可报，早于浓度阈值），误报源是"长得像"的一切；
- MallSenseAI 的选择：`supplemental: True`，**不做替代做补充**——这是对两种误报代价结构的清醒认知，视频检测单独扛不住法律责任。

**B. 多层漏斗 vs 单阈值调优**：
- 单阈值：把所有矛盾压在一个 confidence 数字上，调哪个方向都是错（阈值降→狼来了，阈值升→漏报）；
- 多层漏斗（conf + area + ROI + label + duration + cooldown + 人审）：**每一层用不同的证据维度独立问一次"真的吗"**，单层可以放得宽，整体仍然紧。这和 LnkChat 的 custody→evidence→verify 链路（W10-D3）是同一个设计哲学：**用链式独立证据替代单点强判断**。

**C. 与传统视频厂商（海康/大华行为分析）对比**：
- 厂商方案：算法绑定自家摄像头+平台，封闭且贵，改造成本高（正是域知识里"摄像头改造成本"的来源之一）；
- MallSenseAI：复用存量 IPC + 截图模式 + CPU 推理，部署轻，但时序证据弱（靠 min_stay 补）；
- 差异化位置不在模型（dfire-yolo11n 是公开模型），**在误报治理工程化的完整度**——这恰好是当前最弱也最值钱的一环。

━━━ 8. 架构师思考题 ━━━

**题 1（闭环设计）**：如果让你把 `false_positive` 人审标记变成学习回路，你会回流到哪一层——调 confidence_threshold？调 min_stay_seconds？还是积累成微调样本集？三者的数据量需求、生效周期、过拟合风险各是什么？（提示：想想哪个反馈周期最短、哪个最贵。）

**题 2（错误代价不对称）**：烟火检测如果引入"双模确认"（烟感报警 + 视频检测同时命中才推 critical，只视频命中推 medium 待确认），误报和漏报怎么移动？有没有可能出现"烟感失效 + 视频降级"的双漏路径？这条路径的概率你敢算吗？

**题 3（SLA 定价）**：假设物业要求"月误报 ≤ 2 次、漏报 0 次"才能签单。在一年 0~1 次真实火警的基数下，这两个指标各自需要系统达到什么统计水平？它们能同时满足吗——还是必须用"补充定位"（题 3 里 SLA 只承诺证据质量，不承诺告警完整性）来破局？

━━━ 9. 我的理解变化 ━━━

**以前以为**：安全检测的难点在模型——检测器不够准（mAP 不够高），误报自然就多；换个更强的模型（RT-DETR、更大 backbone）误报就下来了。
**现在知道**：在 base rate 接近零的场景里，**模型精度和有效告警质量是两个指标**。99% 精度的模型在 0 先验场景下产出的仍是误报海洋。真正的杠杆在模型之外的三层：证据维度堆叠（ROI/area/label）、时间维度确认（min_stay/cooldown）、社会维度裁决（false_positive 状态）。误报治理是**系统工程**，不是模型选型——MallSenseAI 代码里那个静态三层漏斗已经是半个答案，缺的另外半个是人审回流闭环。

**第二个变化**：以前把"误报率高"当成产品缺点清单里的一条（和"界面慢"并列）。现在明白它是**商业模式的否决项**——它决定收费模式（人效替代 vs 证据工具）、决定 SLA 能怎么写、决定物业的续费意愿。误报率是这个产品里技术指标和商业指标重合度最高的那一个点。
