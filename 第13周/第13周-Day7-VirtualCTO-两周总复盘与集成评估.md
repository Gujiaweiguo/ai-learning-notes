## 3. MallSenseAI × LangChat 集成评估（今日主菜）

> 这是学习计划给 W13-D7 的专属任务。两周前（W12-D7）的判定是："两边各自完整，中间的桥还没画。"今天用 D5/D6 的产出正式评估：**这座桥现在画到什么程度？什么时候能通车？**

### 3.1 集成成熟度评分卡（0-5 级）

| 集成件 | 两周前 | 现在 | 证据 | 判定 |
|--------|--------|------|------|------|
| 集成架构设计 | 0（未画） | **4** | D5 三份纸：Application 元数据 + Capability 描述符（`lnkchat.<domain>.<verb>`，行业词禁入）+ Connector 配置；三身份三段位图 | 设计完成待评审 |
| 能力选择与排序 | 0 | **4** | D6：第一个能力 `lnkchat.safety.alert.query@v1`（拉模式，不破坏秒级直发边界）；vision/safety 两域拆分 | 有域知识.md P1 条目背书 |
| 视觉侧数据准备 | 2（事件流水有） | **2** | detection_events 是流水账；无日级聚合、无指标口径层、无 Metric 领域对象（entities.py 全是事件型） | **未动工**（S2 任务） |
| 视觉侧度量基础 | 0 | **0** | PPV/漏报未量化——KPI 表还没东西可查 | **未动工**（S1 任务） |
| 平台侧注册体系 | 1（静态 dict） | **1** | catalog.py import 时注册、runtime_binding 空、effects 词表分裂——注册表数据化进了 S3 平台侧任务 | **未动工**（S3 任务） |

**读数：设计成熟度 4/5，实施成熟度 0.5/5。** 两周把桥从"没画"推进到"图纸完成、开工日期排定"；但两岸工地（视觉侧 S1/S2、平台侧注册表数据化）一根桩都没打。**这不是两周学习的失败，恰好是两周学习的产出——图纸（三份纸）+ 施工计划（S1-S3）本来就是动工前的全部交付物。**

### 3.2 集成就绪度模型：木桶 + 关键路径

集成通车 = max(视觉侧就绪, 平台侧就绪)，两侧独立推进：

```
视觉侧就绪 = S1 立尺子（PPV/漏报度量） → S2 出报表（日级聚合+口径层）
             → "capability 有东西可查"
平台侧就绪 = 注册表数据化（DB-backed catalog + provider 自注册）
             + Connector 路由（runtime_binding 从空 dict 到可配置）
             → "capability 有地方可注册"
集成通车（S3）= 第一个能力 lnkchat.safety.alert.query@v1 上线
```

**结构性判断**：视觉侧是**串行依赖链**（S2 依赖 S1 的口径，S3 依赖 S2 的表），平台侧是**单点债务**（注册表数据化是纯平台工程，与视觉侧零耦合）。两侧可完全并行——**集成窗口由慢的一侧决定（木桶效应）**。按 D6 的估算（视觉侧 S1+S2，平台侧注册表数据化），两侧工期同量级，谁卡住谁就是关键路径。今天 notebook 用蒙特卡洛模拟量化了这个判断（3000 次抽样）：集成窗口的中位数落在两侧独立工期预期之后约一个 Sprint 的位置，且**长尾由较慢一侧的悲观情形主导**——等待时间对快的一侧完成度不敏感，对慢的一侧极敏感。"帮慢的一侧"是唯一有效的加速手段。

### 3.3 集成的战略价值判定

**为什么值得集成（而不是各自独立卖）**：

1. **MallSenseAI 的三个死结都指向平台**：误报率是"市场落地难度大的核心原因"（域知识原文）——治理、口径、审计正是 LnkChat 的主武器；单商场无多租户——多租户由平台侧承担；无人脸脱敏（PIPL）——平台的 PII 默认关闭策略（W10 结论）可直接复用。**能力包模式让视觉系统免费继承平台的中台能力。**
2. **LnkChat 平台缺行业证据**：平台有治理体系但无落地场景（W11 结论：最弱的是 Connector）。视觉能力包是第一个真实的企业系统接入者——它将逼着 catalog 数据化、Connector 路由、effects 词表统一三件事从"应该做"变成"必须做"。**集成的过程本身就是平台补债的 forcing function（强制函数）。**
3. **ROI 闭环**：D4 选址案 C 的推理——L5 Vision Agent 住平台 Skill 层，视觉侧到 L4 为止。数字员工卖订阅（平台收入），视觉能力按摄像头/点位收费（应用收入），两层收费不打架。

**集成不成立的假想情形（反向检验）**：如果 MallSenseAI 永远单商场私有部署、且客户永远不需要"问系统问题"（只要推告警），封闭就是终态，三份纸是过度设计。**判定：这个假想在 2B 商管市场不成立**——业主的终极问题是"我的商场今天怎么样"（W12-D5 场景矩阵的根需求），这句话天然是 query 不是 push。集成成立。

### 3.4 集成评估结论（一段话）

> **战略成立、图纸完成、两岸未动工、通车窗口约在 S3 之后一个 Sprint。** MallSenseAI × LnkChat 是"能力包模式"的第一次实战：不搬代码、签三份纸，双方各还各的债（视觉侧立尺子出报表、平台侧注册表数据化），在 `lnkchat.safety.alert.query@v1` 上会合。集成的最大风险不是技术，是**两侧节奏失配**——W14 起主线转入 lnkcre 开发期，视觉侧 Sprint 若无人认领，桥的图纸会过期（Trial 空环的教训：评估和采纳之间必须有正在进行的验证）。

## 4. ADR Health Check（最终版）

### 4.1 本周实锤：ADR-004 示例前缀未同步 ADR-008

今天 grep 验证：`/root/langchat/docs/adr/ADR-004-*.md` 第 70 行 capability 示例仍为 `langchat.vision.detect@v1`——ADR-008（8/21 改名）已过 9 天，示例未更新为 `lnkchat.vision.*`。这是 W13-D5 的发现、今天的实锤。**严重度低（示例非规范）但信号强：改名 OpenSpec change 尚未扫尾 ADR 附件。** 处置：登记为 S3 集成时的同步修正项（示例文件与真实描述符一起改，一次过），不值得单独发 ADR 修订。

### 4.2 悬案裁决：域知识.md「不做客流统计」vs W12-D5 ROI 冠军

**冲突回顾**：域知识.md 明文"不做什么：客流统计"（截图模式的边界声明），但 W12-D5 Business Scene Matrix 把客流（L2 Tracking）排为商业 ROI 最高场景。W13-D3 登记为"集成时必须重新裁决"。

**今日裁决**：
- **边界声明的性质认定**：「不做客流统计」是**当前架构下的诚实声明**（截图模式做不了 Tracking，W12-D4 已论证数据契约差异），不是永久产品边界。它与"不做消防联动"（法律责任边界，永久）性质不同——**架构边界 vs 责任边界必须分开管理**。
- **裁决结论**：L2 客流进路线图 **P2（S4+ 候选）**，不进前 3 Sprint（D6 已裁，商业上要重新卖、技术上要架构换代、度量上依赖 S1 的尺子）。域知识.md 该条目建议改写为："客流统计需视频流 Tracking 管线（独立数据契约），当前截图模式不承载；列入 P2 路线图，前置条件=S1 度量管线 + 场景饱和 + 算力预算。"
- **元教训**：边界文档要带**边界类型标签**（架构边界/责任边界/商业边界），否则三个月后没人分得清哪条能翻案、哪条不能。

### 5.2 预测验证

W12-D7 首评时预测："望远镜分数 7.05，内窥镜复评区间 6.3-6.8。" 实测 6.8，命中区间上沿。**偏差分析**：下探幅度（0.25）小于 LangChat 侧四周累计下探（0.8），原因是 MallSenseAI 只精读两周（下探主要发生在第二周 D5/D6 的 catalog/entities 内窥镜），且其测试纪律托住了 Code Health 的底。**方法论结论：新对象首评必为望远镜分，+1 周内窥镜复评的预期下探 0.2-0.5——这条规律在两个对象上复现，可以定稿为标准评审动作。**
