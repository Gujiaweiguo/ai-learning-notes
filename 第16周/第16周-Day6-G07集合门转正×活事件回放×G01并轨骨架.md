**门语义**（g07-draft §2 的实现，锚定对象从「文本行」换成「集合关系」）：

| 检查 | 判决 | 今日活事件回放（对 origin/main `94b83434` 实跑） |

| fail-closed | 基线缺失/空、rev 不可读 → 直接红 | 正常输入，未触发 |

**两个非显然的设计决策**（docstring 已记）：

1. **泄漏不豁免 snapshot 痕迹**：语义模型 yaml 里有文本痕迹的新表，正锚降级 DRIFTED，但泄漏检查仍 BROKEN。理由：yaml 是**结果快照**，changes/ 是**过程记录**——「登记 or 显式不入域」两种裁决都必须以 change 形式留痕才算 citing。这正是 G-01 存在的同款理由（文件无治理头 → 改了没人知道），不能在自己的门里开倒车。
2. **citing 扫描排除 `_drafts/`**：草案无裁决效力（下划线目录约定）——今天起草的并轨骨架放在 `_drafts/` 下，被自己刚转正的门判定「不算立案」，机制自洽。

**--change 承认路径预演**：临时造一个引用全部 7 表的 change → verify 判 **GREEN**（exit 0）。citing-action 定价模式的完整生命周期走通：门不禁止加表，只要求裁决——**变化留痕，不是禁止变化**。

**转正过程抓出的四个 bug**（每个都有教训值，比一次通过更有价值）：

1. **POSIX ERE 方言坑**：`git grep -E` 不支持 `(?:` 非捕获组（rc=128 fatal）。修复：粗滤交给 git（固定串 `CREATE TABLE`），精判留给 Python re——**方言隔离，正则复杂度留在可控的一侧**。
2. **正则交替优先级**：未分组的 `CREATE TABLE A|B|C` 实际是 `(CREATE TABLE A) | (B) | (C)`——`CREATE INDEX … ON tbl (` 也命中，归因多行假阳性。暴露路径：回放输出里 `leasing_policy_versions` 命中 6 行，「单表单 CREATE」的直觉红旗。教训：**交替必须外层分组，且对输出的「形态预期」要和逻辑一样硬**。
3. **目录名前缀碰撞**：`migrations` 是 `migrations-pg` 的前缀，side 判定把 PG 迁移标成了 `mysql:`。修复：`d + "/"` 精确段匹配。**这是 D4 Identity 门「子串碰撞」坑的目录版重演**——`gov_snap_lease_daily ⊃ snap_lease_daily` 那次修的是表名词边界，这次是路径词边界：凡是「名字包含名字」的场景都要精确边界，教训开始泛化成规则。
4. **selftest 自己的 bug**：M2 把 change 子目录当 `--changes-dir`（应为 changes 根）传了，豁免路径哑火、M2 FAIL。M2 是六突变里唯一「期望绿」的——它 FAIL 说明「门坏了**或**测试坏了」两种可能，逐一排查后是后者。**selftest 不是门的配件，是门的第一用户**；fail-closed 哲学同样适用于测试本身。

**四个 bug 的共同点**：没有一个被「代码看起来对」防住，全部被**运行时证据**抓住（fatal 输出 / 多行归因 / side 标错 / M2 红绿灯错）。这恰好是本周主题的微缩版：静态审查守不住动态世界，门如此，门的实现也如此。

## 5. Today's Question 的回答

**计数比对和集合判决都能发现 477→484，为什么必须是集合门？因为计数门缺的不是灵敏度，是「对象」。四个结构性盲区，每一个都无法靠调阈值补上：**

1. **无对象性 → citing 定价无法执行**。计数门说「多了 7」；citing-action 要求「每张表一张裁决」。不知道是哪 7 张，登记/不入域的裁决就无从谈起——G-07 的核心机制是**给对象定价**，定价必须对象级。这是「异常检测」和「对象裁决」的差别：前者输出标量（一个数变了），后者输出判决列表（每张表一个 verdict + 归因 + 该谁管）。
2. **无方向性 → 等量换血全盲**。删 1 加 1，477→477，计数门绿灯——selftest M5 的构造正是这个形态。表宇宙「换血」（旧表被替换/重命名）恰恰是 schema 演进的常态（昨天的 +7 就伴随 unit_pricing 历史表改造），等量场景不是刁钻 corner case，是日常。
3. **无归因链**。集合门的每个 BROKEN 挂着 `pg:000227@L18`——拿到判决就能直奔建表语句；计数门拿到 +7 之后一切才刚开始（哪个 diff？哪次 pull？）。**检测的价值一半在报警，另一半在报警里带着地址**。
4. **无负锚**。计数对「谁消失了」同样失明（等量换血的另一面）：死登记——语义层说有、数据库没有——是比孤儿更阴的腐烂方向（说谎的台账）。

**ERP 映射**：这就是 26 年 ERP 里「总账控制总额 vs 明细账+凭证链」的差别。库存月盘点，总数对上了敢签字吗——不敢，因为**串户、错仓、以次充好全部不改变总量**；必须逐货架对标签。银行对账单余额一致就是平了吗——不是，余额调节表只是下限，**逐笔勾稽**才能抓出「金额相同但对象错了」的隐性错配。控制总额（count）是 necessary not sufficient——ERP 差异分析（variance analysis）永远落到科目级/单据级/明细级，**不到对象的对账是假对账**。S2 探针「数 commit」→「数表」的说法其实还保守了：数表仍是计数，真正的升级是**集合判决**——这正是今天把 mini 门转正时把输出定成 `results[]` 逐表判决、而不是 summary 计数的原因。

## 8. 理解变化（保留学习期传统）

以前以为：D5 说「S2 只数 commit 看不见表」，教训是探针要「看得更细」（看 commit 内容）。现在知道：**关键不是粒度是对象**——S2 升级为「数表」如果只是数个数，对等量换血照样全盲；真正的升级是判决对象从标量变成集合，输出从计数变成逐对象 verdict 列表。「看内容」是手段，「逐对象裁决」才是语义。以前还以为 selftest 是门交付前的例行配件；现在知道 **selftest 是门的第一用户**——今天四个 bug 里一个是 selftest 自己的，而且是它先 FAIL 才逼出排查：期望绿的突变失败时，「门坏了还是测试坏了」必须都当真，这就是 fail-closed 对测试自身的反身应用。第三个：以前以为转正 = 把 ipynb 代码抄进 .py；现在知道**转正的实质工作是让代码离开 notebook 的温室**——ipynb 里不会遇到的 ERE 方言、目录前缀、CLI 边界全部在转正当天现身，四个 bug 三个在「ipynb 原型根本没走过的路径」上。原型证明逻辑可行，转正证明工程可用，两者之间隔着整个真实环境。
